# Lowcode 局部重渲染优化设计方案

## 1. 背景与结论

当前 `packages/lowcode` 已使用 patch 对 `QuestionJson` 做不可变更新，但 React 层仍按整棵树订阅和渲染：

- `QuestionDesigner` 订阅 store 的任意变化，并递增根组件版本。
- `FormWidget` 每次渲染都通过 `getJson()` 获取整棵 JSON，再递归创建所有 `DesignerNode`。
- `DesignerNode` 和 renderer 的 `RenderNode` 没有使用 `React.memo`。
- `getJson()` 和 `commit()` 使用 `structuredClone`，无法依靠对象引用稳定性完成细粒度判定。

因此，修改一个节点属性时，当前行为是“数据只修改一个节点，React 重新执行整棵组件树”。本方案目标是将其改为“目标节点及其真实依赖者更新，无关节点保持不渲染”。

## 2. 目标与非目标

### 2.1 目标

1. 修改一个节点的普通属性时，无关节点不重新渲染。
2. 修改一个答案字段时，无关字段控件不重新渲染。
3. 插入、删除、移动节点时，只刷新受结构影响的父容器和相关路径。
4. 保持现有 `QuestionJson`、`QuestionPatch`、公开入口和撤销/重做语义不变。
5. 通过测试和 Profiler 指标证明优化有效，而不是仅依赖代码结构推断。

### 2.2 非目标

- 不在本阶段改变契约 schema 或 widget registry。
- 不引入跨页面的全局运行时状态。
- 不为了减少渲染而牺牲组件属性的可预测性或 patch 校验。
- 不把所有组件拆成独立 React root；这会增加生命周期、事件和拖拽管理复杂度。

## 3. 设计原则

### 3.1 状态按职责拆分

设计器 store 继续保存文档和编辑状态，但 React 订阅必须按 selector 分片：

```text
DesignerStore
|- document: QuestionJson
|- selection: selectedId
|- interaction: draggingId / dropTargetId / dropPosition
|- history: undo / redo metadata
`- dependencyIndex: derived dependency edges (optional phase 2)
```

组件节点通过 `nodeId` 读取自己的节点；选中态、拖拽态等高频 UI 状态不应迫使所有节点订阅完整文档。

### 3.2 结构共享

每次 patch 只复制从根到变更点的路径，未受影响的节点、options 和 sibling 数组保持原引用。禁止在每个 render 读取全量 `structuredClone` 结果。

```text
old root -> page -> group -> target
new root -> page' -> group' -> target'
                    other children === old other children
```

`structuredClone` 只用于历史快照、外部导出和不可变边界，不用于 React 的日常读取。

### 3.3 依赖显式化

属性表达式或联动规则应注册为依赖边，例如：

```text
node:b.visible <- node:a.options.score
```

没有依赖边的节点不因 `a` 的变化而刷新。依赖图属于派生索引，不改变对外 JSON 格式。

## 4. 推荐架构

### 4.1 Store API

使用 Zustand 的 selector 能力，或在现有 `DesignerStore` 上增加等价 API：

```ts
interface DesignerStore {
  getJson(): QuestionJson; // 导出/回调使用，可返回安全副本
  getNode(nodeId: string): WidgetNode | null;
  subscribeNode(nodeId: string, listener: () => void): () => void;
  subscribeSelector<T>(selector: (state: DesignerState) => T, listener: () => void, equality?: EqualityFn<T>): () => void;
  updateOptions(nodeId: string, options: Record<string, JsonValue>): void;
}
```

实现上优先使用 `useSyncExternalStore` 对接 selector，而不是由 `QuestionDesigner` 用 `setVersion` 强制整个页面刷新。若保留 vanilla store，则需要提供稳定的 `getSnapshot` 和比较函数。

### 4.2 节点订阅组件

设计器和 renderer 都采用“节点数据容器 + 纯展示节点”结构：

```tsx
const DesignerNode = React.memo(function DesignerNode(props: DesignerNodeProps) {
  const node = useNode(props.store, props.nodeId);
  const selected = useSelected(props.store, props.nodeId);
  if (!node) return null;
  return <DesignerNodeView node={node} selected={selected} ... />;
});
```

`React.memo` 只解决 props 稳定时的跳过问题，真正的关键是 `useNode(nodeId)` 只返回该节点的引用。不要把整棵 `QuestionJson` 或新建的深拷贝对象作为每个节点的 prop。

### 4.3 结构节点与叶子节点

- 容器组件订阅自己的 `widgetList` ID 列表和容器 options。
- 叶子组件订阅自己的 options，以及它实际使用的答案字段。
- 兄弟节点列表变更时，只重渲染发生插入/删除/移动的父容器。
- 父容器的普通属性变化不应导致子节点重新渲染，除非该属性确实传给子节点或命中依赖图。

## 5. 设计器改造方案

### 5.1 移除根版本刷新

将 `QuestionDesigner` 当前的全量 `store.subscribe(() => setVersion(...))` 改为：

1. 根布局只订阅选择态、拖拽态和根节点 ID 列表。
2. `SettingPanel` 只订阅当前 `selectedId` 对应节点。
3. `FormWidget` 将节点 ID 传给 `DesignerNode`，不传完整节点快照。
4. `onChange` 仍在提交 patch 后调用 `getJson()`，作为外部持久化快照，不参与节点渲染。

### 5.2 选择态与交互态

选择态变化会影响 CSS class，因此每个节点可订阅 `selectedId === nodeId` 的布尔 selector。拖拽 over 状态同理按 node ID 订阅。这样选择一个节点时，最多是旧选中节点和新选中节点各更新一次。

### 5.3 属性编辑

`SettingPanel` 的字段控件使用当前节点 options 的 selector。输入过程建议采用两种模式之一：

- 即时提交：每个输入事件提交一个 `updateOptions` patch，仅当前节点更新。
- 草稿提交：字段在本地维护草稿，失焦或确认时提交一次 patch，减少历史记录数量。

无论选择哪种模式，不能通过 `setJson({ ...json, ... })` 让整个设计器以全量快照重新分发。

## 6. Renderer 改造方案

### 6.1 节点 memo 化

将 `RenderNode` 拆为容器节点和叶子节点，并使用 `React.memo`：

```tsx
const RenderLeaf = React.memo(function RenderLeaf({ node, value, ...rest }: Props) {
  const Field = fieldComponents[node.type];
  return <Field node={node} value={value} {...rest} />;
});
```

回调 `onAnswerChange` 使用 `useCallback`，避免因根组件每次 render 创建新函数而使所有叶子节点失去 memo 效果。回调应按字段名更新答案，不携带整棵答案对象。

### 6.2 答案状态

答案数据应按字段读取：

```ts
const value = useAnswer(name);
```

答案更新时保持结构共享，只替换目标字段所在的 map。若暂时无法引入字段级 store，至少在 `RenderNode` 上通过自定义比较函数比较 `answerData[name]`，而不是比较整个 `answerData` 引用。

### 6.3 外部 setJson

`setJson` 仍需支持整份文档替换，但应先计算节点 ID 到节点引用的变更集合：

- 引用和内容均未变的节点复用旧引用。
- 内容变化的节点替换引用。
- 新增/删除节点只影响对应父容器。

如果外部输入无法提供稳定引用，则使用 `id + 结构哈希` 做复用判定；哈希只在 `setJson` 边界计算，不在每次 render 计算。

## 7. Patch 与历史记录

### 7.1 结构共享 patch

将 `applyQuestionPatch` 从“先深拷贝整棵 JSON 再修改”改为路径复制：

1. 建立 `id -> parent path` 索引。
2. 复制目标节点、父数组和祖先节点。
3. 其他分支直接复用旧引用。
4. 最后执行 normalize，并保证 normalize 本身也具备引用复用能力。

### 7.2 历史快照

撤销/重做可以保存结构共享版本，或在写入历史时单独 deep clone。历史快照的内存成本不应转嫁给渲染路径。历史切换属于整份文档替换，可以接受受影响树的大范围更新。

## 8. 依赖图与联动属性

第一阶段可只支持显式依赖 API：

```ts
registerDependency({ source: 'node-a.options.score', target: 'node-b.options.visible' });
```

更新源节点后：

1. 计算直接依赖目标集合。
2. 对目标集合重新求值。
3. 只通知目标节点和必要的祖先容器。

第二阶段再支持表达式解析、循环依赖检测和批量更新。依赖图必须有最大深度或访问集合，避免循环联动导致无限更新。

## 9. 验收标准

### 9.1 功能验收

- 修改节点 A 的文本、颜色、选项等属性，节点 B/C 的 DOM 不被卸载重建。
- 选择态切换只更新旧选中节点和新选中节点的 class。
- 插入、删除、移动后组件顺序、拖拽目标、撤销/重做结果与当前行为一致。
- 预览和答题态的答案值、校验和 `onChange` 行为不变。

### 9.2 渲染验收

新增测试用渲染计数器记录每个 node ID 的 render 次数：

```text
updateOptions(A) => A + 1, unrelated B/C + 0
updateAnswer(nameA) => fieldA + 1, unrelated fieldB + 0
select(A -> B) => A + 1, B + 1, others + 0
```

允许容器因其 child ID 列表或必要上下文变化而更新，但无关叶子节点必须保持 0 次新增渲染。

### 9.3 性能基线

以 100、500、1000 个节点分别测量：

- 单属性更新的 React commit 数和 commit duration。
- 更新前后无关节点 render 次数。
- 首次渲染、插入节点、移动节点、撤销操作的耗时。
- 历史快照内存占用。

建议把基线写入性能测试，不把绝对毫秒数作为唯一门槛；核心门槛是更新规模从 O(N) 降为 O(受影响节点数 + 祖先路径)。

## 10. 分阶段实施

### Phase 1：低风险渲染隔离

1. 为 `DesignerNode`、容器/叶子 renderer 增加 `React.memo`。
2. 稳定 `onAnswerChange`、节点回调和静态 props。
3. 增加渲染计数测试与 Profiler 基线。

### Phase 2：按节点 selector

1. 给 store 增加 `getNode`、selector 订阅和 `useSyncExternalStore` 适配。
2. `FormWidget`/`QuestionRenderer` 改为传 `nodeId` 或订阅单节点。
3. 将选择态、答案态改为字段/节点级订阅。

### Phase 3：结构共享与依赖更新

1. 重写 patch 应用中的路径复制和 normalize 引用复用。
2. 加入依赖索引和联动属性通知。
3. 增加大规模节点性能回归测试。

## 11. 风险与回滚

- memo 比较函数遗漏字段会造成 UI 不更新；必须优先使用完整 props 类型和针对性测试，避免手写过宽的 `areEqual`。
- selector 返回新数组会导致订阅失效；节点 ID 列表需要缓存或浅比较。
- 结构共享改造可能影响历史和 normalize；Phase 3 应保留旧 patch 实现作为测试对照或 feature flag 回滚路径。
- 联动表达式存在循环依赖风险；首版只允许有向无环依赖并在注册时校验。

## 12. 交付物

- store 的 selector / 节点订阅 API。
- 设计器节点级渲染组件和 renderer 节点级渲染组件。
- patch 结构共享实现及兼容测试。
- render count、Profiler 和大规模节点性能测试。
- 发布前执行 lowcode 包的完整 `verify`，并按仓库规则递增版本、发布新包后更新消费端依赖。
